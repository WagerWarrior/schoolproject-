WHAT WE ARE BUILDING
We compare enrollment information alone (A, 11 original inputs) against
enrollment plus six first-semester inputs (B, 17 original inputs).
The answer is 1 for recorded Dropout and 0 for Enrolled or Graduate.
Still enrolled does not guarantee eventual graduation. Without dropout dates,
this is retrospective classification, not a validated forecast of future dropout.

WHAT SCIKIT-LEARN DOES
Scikit-learn is a Python library. It provides the learning algorithms, not
pretrained weights for our project. The course instructions explicitly list
scikit-learn as an example Python library under Technical requirements, page 4:
https://eclass.yorku.ca/mod/resource/view.php?id=4550502

HOW LOGISTIC REGRESSION LEARNS
It combines input values with learned weights and an intercept, then converts
the result into a score between 0 and 1. During fit(), an optimizer adjusts the
weights to reduce the training objective (prediction loss plus a penalty).
Our code allows up to 1000 iterations; it may stop sooner after convergence.
We do not choose the learned weights ourselves. They come from fitting our data.
Predicting does not update weights. New learning requires deliberate retraining
using examples with known outcomes. Calibration needs checking before treating
scores as reliable individual probabilities.

PREPARATION
We kept documented unknown categories and valid zeros. We encoded seven nominal
fields with one-hot encoding: separate 0/1 columns for their categories.
We standardized numerical inputs for logistic regression:
scaled value = (original value - training mean) / training standard deviation.
The two existing binary fields remain unchanged. Encoding and scaling are fitted
separately within each cross-validation training fold.

EVALUATION DESIGN
3539 training students; 885 test students held aside. Stratified split, seed 42.
Five-fold cross-validation within training: learn on four parts, validate on one.
Every training student has one validation prediction per model, produced without
training on that row. A and B use the same folds. No test scores computed yet.
Initial cutoff: score >= 0.5 means predict dropout. No tuning yet.

RANDOM FOREST TRAINING — STEP 11
A random forest combines many decision trees. Our initial forest has 100 trees.
Each tree learns from a random sample of training rows drawn with replacement
(bootstrap sampling): some students may appear more than once in that sample.
Each split considers a random subset of input features. This creates variation
between trees. Scikit-learn averages the trees' class probability estimates;
our code predicts dropout when the average score is at least 0.5.
This can reduce dependence on one tree, but does not guarantee better results.

Simple setup:
RandomForestClassifier(n_estimators=100, random_state=42, n_jobs=-1)
n_estimators is the number of trees; random_state makes the run reproducible;
n_jobs=-1 uses available CPU cores. We left other settings at their defaults,
including unrestricted tree depth. No class weighting or tuning yet.
As with the single tree, we one-hot encode categories but do not scale numbers.
Preprocessing is fitted inside each training fold. We reuse the same five folds
for A and B, and never load test inputs or answers in this training script.

Smaller C applies a stronger penalty on large weights (regularization).

RANDOM FOREST LEAF-SIZE TUNING — STEP 15
A leaf is the endpoint of a tree where it makes a prediction. min_samples_leaf
sets the minimum number of training samples required in each leaf. Increasing
it prevents splits that would leave an endpoint with too few training samples.
It does not specify how many questions to ask or how many trees to build.
In a bootstrap forest this refers to samples used by each individual tree,
not a requirement about validation students or every student in the dataset.

We compared 1, 5 and 10. Each forest still has 100 trees, seed 42, default
unrestricted depth and cutoff 0.5. Only min_samples_leaf changes. For each
setting and input version, we fit five fresh pipelines: 30 fits in total.

EXPLAINING WHAT THE MODEL LEARNED — STEP 18
We used two views without changing the final model:
1. Read its learned weights. Positive pushes the dropout score up; negative
   pushes it down, holding all other inputs fixed. This is a conditional model
   relationship, not evidence that changing that feature causes an outcome.
2. Permutation importance: shuffle one column in validation rows, keeping the
   others unchanged, and measure how much average precision drops. Repeat five
   times in each of five folds. Encoding/scaling/model fitting still happens
   only on the corresponding training-fold rows. No test rows are loaded.

In simple terms: mix up one column and ask, "Does the model become worse at
ranking students by recorded dropout outcome?" A larger decrease suggests more
reliance on that column. This uses average precision, not accuracy or F1.

Largest mean decreases in validation average precision:
Courses passed in semester one: 0.4582
Courses enrolled in semester one: 0.0672
Credited courses in semester one: 0.0447
Degree program: 0.0267
Application mode: 0.0130
Age at enrollment: 0.0098
These are changes in a metric, not shares of total importance or probability.
Each value averages 25 measurements. Standard deviations are descriptive
variation across repeats/folds, not confidence intervals or significance tests.

Courses passed had final weight -2.4692 per training standard deviation: more
passed courses lowers the score when other inputs stay fixed. Courses enrolled
had weight +0.8958: with passed courses held fixed, more enrolled raises the
model score. This does not mean that enrolling in more courses causes dropout.
Credited-course weight was +0.6985; do not turn this conditional association into
a causal story. Average grade weight was -0.0885 and its shuffled-column effect
was small (0.0014 mean, 0.0024 standard deviation). The model uses academic
progress, especially courses passed, rather than relying mainly on average grade.

Limits: related columns share information, so one can look less important when
another captures a similar pattern. Shuffling can produce impossible combinations
such as more courses passed than enrolled; this can inflate estimated importance.
Category weights and standardized numeric weights should not be ranked blindly
as a single universal measure. Small or negative permutation values are not proof
that a field is useless. No inputs were removed and no final settings changed.

Suggested report wording: "For the locked logistic-regression setup, validation
permutation analysis identified first-semester courses passed as the strongest
input in this diagnostic. Its negative coefficient associates more passed
courses with lower predicted dropout scores, holding other inputs fixed.
These results describe model behavior, not causal effects."

STREAMLIT APPLICATION — STEP 19
Streamlit turns a Python script into an interactive page in a browser.
We wrote app.py using ordinary if/else statements and Streamlit widgets.
The app does not retrain the model or change the final cutoff.

1. Results page: reads saved final test metrics and shows the confusion matrix.
   A model selector compares initial A/B validation scores, clearly separated
   from final B test results. No test evaluation is rerun to draw the page.
2. What mattered page: reads the saved validation permutation importance table.
   A slider chooses how many columns to display. Interpretation limits appear
   beside the chart; no causal or individual-risk claims are made.
3. Made-up profile page: collects the 17 original inputs in a form, puts them
   into a one-row pandas DataFrame, and calls the saved pipeline's predict_proba.
   The pipeline applies the SAME learned encoding, scaling and weights as before.
   Score >= 0.3 means the example is classified as dropout. We do not use the
   classifier's default predict() rule, because it would use a different cutoff.

Forms submit all input values together when Calculate example score is clicked.
No profile input is written to disk or a database. Use fictional examples only.
The result is called a model score, not a confirmed probability. The app warns
that it is educational and unsuitable for real student decisions. It checks that
passed/credited/no-assessment counts do not exceed enrolled courses. This is
basic validation, not a guarantee that every allowed profile is realistic.

Run: streamlit run app.py, then visit http://127.0.0.1:8501.
The local server is bound to 127.0.0.1 and usage-stat collection is disabled.
On another computer, prepare the data/split using scripts 01-04, then run
19_build_app_model.py. It rebuilds the locked model from training data only,
without rerunning the test. It refuses to overwrite an existing model artifact.

The app is local, not deployed online. GitHub holds the app code, requirements,
setup instructions and aggregate outputs. It excludes raw data and fitted models.
The first version implements model comparisons, global feature explanations and
fictional-profile predictions. Cohort filters and per-profile contributions are
not implemented yet. Fairness analysis and the final report are still outstanding.
